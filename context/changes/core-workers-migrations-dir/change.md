## Intent

A Worker generated by `softure-deploy init --host=cloudflare` for an app with `@softure-ai/jobs` imports
`softure.config` at its start (the scheduled handler needs it before any request). wrangler bundles the Worker into
one ES module, and workerd leaves that module's `import.meta.url` undefined, so every module package's
`resolveMigrationsDir(import.meta.url, "../migrations/")` throws and the Worker does not start. OpenNext sets a
placeholder `import.meta.url`, but only on its first request. An adopting app worked around it with an extra
first import that assigns `import.meta.url`; the fix belongs to the package so no generated Worker needs it.

## Context

`@softure-ai/core` 0.2.9: `resolveMigrationsDir` throws whenever the module URL is undefined (written for CJS
bundles). `isWorkersRuntime()` (RP-7) already tells workerd apart. Only `softure migrate` reads the folder, under
Node; a Worker never does.

## Scope

- `resolveMigrationsDir`: on Workers with no module URL, a placeholder `file:` URL under the bundle; Node keeps the
  CJS-bundle error.
- Unit tests in `foundation/core`, and a workerd test in the example app's Workers suite: a Worker that enables a
  module in its config, served by `wrangler dev`.
- CHANGELOG and a patch release of core (0.2.10). The deploy template needs no change.

## Decisions (auto)

- Fix in core, not in the template: the root cause is a module package failing to load on a supported runtime; a
  template workaround would leave every hand-written Worker (and the example) exposed.
- Placeholder base `file:///bundle/worker.js` (workerd mounts the bundle at `/bundle`), so `defineModule`'s
  `file:` check still holds.
- The workerd test lives in the example app's Workers suite, which already installs wrangler; the root workspace
  gets no workerd dependency.
