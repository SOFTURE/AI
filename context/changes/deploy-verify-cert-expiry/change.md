## Intent

An app learns from its deploy that its certificate is about to expire, not from its users. An optional
`verify.tlsMinDays` in `deploy.json` makes `softure-deploy verify` open one TLS connection to the host of the
verified `https://` URL, read the peer certificate and add a `tls` row to the report: days left, the expiry date and
the issuer. Fewer days left than the minimum, an untrusted certificate or no certificate at all fails the run
(exit 1). Without the key nothing changes.

## Context

Input: [`backlog-input.md`](backlog-input.md) (roadmap item **DF-6**, from DP-4's research question 1: `fetch`
refuses an invalid or expired certificate, but nothing warns before expiry).

## Constraints

- Owns `tools/deploy/src/verify/`, `tools/deploy/schema/` and their tests, plus the `verify` part of the package
  README and the CLI's verify command.
- DF-5 adds another optional key to the same `schema.ts` in parallel; the second to merge takes `master` and
  regenerates `schema/deploy.schema.json`.
- No request to a real production URL in tests: a local TLS server with a certificate generated by `openssl`.

## Process

- **Research:** done ([`research.md`](research.md)): the `node:tls` details (SNI for IP hosts, what the peer
  certificate carries, how an untrusted certificate is reported) decide the shape of the check.
- **Framing:** skipped. The problem and the outcome are fixed by the roadmap item; there is one obvious place for
  the check (the verify engine) and no product choice left open.
