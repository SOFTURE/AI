## Compose and dotenv facts the code relies on

- Required variables in compose: `${NAME:?message}` fails when `NAME` is unset **or empty**; `${NAME?message}` only
  when unset. `$$` is a literal dollar, so `$${NAME:?}` is not a variable.
- `${NAME}`, `${NAME:-default}` and `${NAME-default}` are optional; `env render` does not write them.
- In a Compose env file, a single-quoted value is taken literally (no interpolation, no escapes); an unquoted value
  is interpolated (`$`), and ` #` starts a comment. A value holding a newline or a single quote has no literal
  single-line form, so the renderer refuses it (naming the variable, not the value).

## Answers to the roadmap unknowns

1. **Release notes read `git log` only, no GitHub API.** The merge commit subjects carry the pull request number and
   title (both this repository's `Merge <branch>: <title> (#N)` and GitHub's merge and squash forms), so the report
   needs no token and runs the same locally and in CI. Links come from `--repo-url` or the Actions variables
   `GITHUB_SERVER_URL` and `GITHUB_REPOSITORY`. API enrichment (labels, authors) can come later without changing the
   command.
2. **Range:** `--from` defaults to the latest tag reachable from `--to`'s parent that matches `--match` (a git glob,
   e.g. `v*` or `app@*`), so a release job passes only the new tag. With no earlier tag, the whole history is the
   range (a first release).

## Risks

- Option injection through a ref (`--from=--output=x`): refs are validated (no leading `-`, no `..`, a safe
  character set) and git runs through `execFile` with an argument list, never a shell.
- A value printed by accident: the env command reports only names and counts; a test runs the command with a
  sentinel value and asserts it is absent from every output stream.
