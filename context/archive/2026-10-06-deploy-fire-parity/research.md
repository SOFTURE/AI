# Research: deploy-fire-parity

Read side by side on 2026-10-06: FIRE_TRACKER at `7aad63a` (read only) and `@softure-ai/deploy` 0.1.2 on `master`
`225882e`. FIRE files read in full: `src/lib/env-prod.ts` (+ test), `scripts/render-env-prod.mts`,
`src/lib/release-notes.ts` (+ test), `scripts/release-notes.mts`, `.github/workflows/release.yml`, `auto-release.yml`,
`release-opis.yml`, `docker/server/gateway.sh`, `docker/server/deploy.sh`, `scripts/deploy-via-gateway.sh`,
`scripts/verify-production.sh` (743 lines).

Decisions per row: **port** (into the CLI in this change), **gap** (generic, but in a file DF-7 owns now: a new
roadmap item), **app** (FIRE-specific, listed in the README), **kept** (the package already does it, or does it
better on purpose).

## 1. `env render` vs `render-env-prod`

| FIRE | Package | Decision |
| --- | --- | --- |
| Names from compose: `${X:?}` required, `${X:-}` optional; optional names are written **when set**, omitted otherwise (`MCP_ALLOW_WRITES`, `REGISTRATION_CLOSED`, `ADMIN_EMAILS`) | optional forms skipped entirely: an optional runtime switch can never reach the server | **port**: `${X:-…}` and `${X-…}` names are written when set and non-empty; bare `${X}` stays skipped (it also matches `${TAG}`, `${HOME}`, which the deploy script or the shell set) |
| A name required anywhere is required (`:-` elsewhere does not weaken it) | stricter form wins among required forms | **port** (same rule extended to optional forms) |
| Header comment `# generated by the release, do not edit on the server` | no header | **port** (one comment line; compose and `deploy.sh`'s `read_env` ignore it) |
| Quoting: bare unless space, `#`, `"`, `$`, `\`; refuse `'` and newline | bare only for a safe set, else single quotes; refuse `'`, CR, LF | **kept** (same outcome, a stricter bare set) |
| All problems at once | `missing` and `unsafe` listed together | **kept** |
| Optional switch read from Environment **variables** before secrets (a secret `1` masks every `1` in logs) | the workflow passes one JSON of secrets | **gap** (workflow input for non-secret values; DF-7 owns `deploy-app.yml`) |
| `IMAGE_TAG` written into `.env.prod`, so cron and manual `docker compose` on the server work | `deploy.sh` exports `TAG`; a manual compose has none | **gap** (server script, DF-7 owns it) |
| `APP_ORIGIN`/`APP_DOMAIN` of the image build must equal the runtime secret (L-117) | the workflow has no build args | **gap** (build args are a workflow input; the comparison rides with them) |
| `WAITLIST_UNSUBSCRIBE_SECRET` at least 32 characters | none | **app** |
| Output names only, file mode 600 | same, written through a temporary file | **kept** |

## 2. `release-notes` vs FIRE's release report

FIRE's report is a **living release body**: sections between `<!-- release:<key> -->` markers (overview, pipeline
status, deployments) rewritten in place on each run, the owner's text above them untouched; the overview lists the
roadmap's `done_code` rows (ID, change, outcome), the commit and the compare link. It does not group by type or label,
which answers the item's unknown: there is nothing to regroup in DP-1's two sections.

| FIRE | Package | Decision |
| --- | --- | --- |
| Sections between markers, owner text kept, a rewrite replaces in place | prints a whole body | **port**: `--body=<file>` writes the report into its own marker section of an existing body |
| Overview: roadmap rows with `done_code` / `done kodowo` from `## At a glance`, status = last cell, `\|` inside a cell | none (git only) | **port**: `--roadmap=<file>` adds a "Roadmap items" table (SOFTURE roadmaps share the table) |
| Pipeline status table, deployments history (image, digest, backup, row counts before and after), written by a final job from the gateway's machine lines | none; the workflow has no report job | **gap** (needs a report job in `deploy-app.yml` and machine-readable server output) |
| `release-opis.yml`: replace the text above the report (cloud sessions cannot edit releases) | none | **app** (an owner workflow of FIRE; `--body` keeps the text above, which is what it relies on) |
| Times in Europe/Warsaw | commit date only | **kept** |

## 3. Workflow (`release.yml`, `auto-release.yml`) vs `deploy-app.yml`

| FIRE | Package | Decision |
| --- | --- | --- |
| Tag pattern `vYYYY.MM.DD[-N]`, commit must be on `master` | any Docker tag, no branch check | **gap** (refuse a tag not on the default branch) |
| Gates and integration tests in the same run before deploy | the caller's own workflows | **app** |
| Image built once as `sha-<sha>`, tested, then re-tagged with the release tag (`imagetools create`), digest output | built from the tag, digest output | **kept** (no separate integration image to reuse) |
| Build args from repository variables | none | **gap** (with §1's origin comparison) |
| `.env.prod` and a short-lived `ghcr-token` (the job's `GITHUB_TOKEN`) as one tar on stdin; `docker logout` after | `.env.prod` alone on stdin; the server holds a permanent read-only registry login | **gap** (the protocol now changes in DF-7; the token belongs to the same archive) |
| Gateway output kept as an artifact and in the job summary | none | **gap** (with the report job) |
| `auto-release.yml`: free date tag, release created, deploy dispatched (an agent cannot push tags) | none | **gap** (a reusable "cut a release" workflow) |
| Weekly `docker image prune` cron on the server (DEPLOYMENT.md §9) | none | **gap** (server retention, with §4) |

## 4. Server side (`gateway.sh` + `deploy.sh`) vs `init`'s `deploy.sh` and DP-3's steps

FIRE splits the server in two: a small **gateway** installed once (forced command, `deploy <tag>` and a read-only
`status`, one-line command, `read -r -a`, no `eval`), which pulls the image and runs the **deploy script shipped
inside the image** (`/app/deploy-bundle/`). The facts were sent to DF-7, which owns shipping server files.

| FIRE | Package | Decision |
| --- | --- | --- |
| `status` command (tag, containers, health), read only | `deploy <tag>` only | **gap** |
| Current files and `.env.prod` saved before the swap, restored when the swap fails; `.env.prod.prev` kept | `.env.prod` overwritten | **gap** |
| Traefik recreated when `traefik.yml` changed (a bind-mounted file is not reloaded) | not handled | **gap** |
| Health polled after `up` (30 tries) | `compose up --wait` | **kept** (`--wait` waits for the healthchecks) |
| Machine lines `krok\|…`, `liczniki\|…`, `kopia\|…`, final `wynik\|ok`; the client fails without `wynik\|ok` | plain messages, exit code | **gap** (feeds the report job of §2) |
| Backup: `pg_dump \| gzip`, `--no-owner --no-privileges`, `--exclude-table-data=auth_attempts` (IP addresses must not live 30 days) | `--format=custom` | **port** `--exclude-table-data`; **kept** the custom format (compressed, restorable selectively with `pg_restore`; no owner or privilege statements are forced on a restore by it) |
| Backup integrity: `gzip -t` and non-empty | exit code of `pg_dump` | **port**: the file must start with the custom format's `PGDMP` header |
| Retention: at most 10 by count **and** none older than 30 days (privacy policy), also by a daily cron | newest 7 by count | **port** `--max-age-days` (by the timestamp in the file name, so a copied file keeps its age); **kept** 7 as the default; the daily cron is a **gap** (server script) |
| Schema guard: migration count of the image ≥ count in the database | checksums, missing and out-of-order files against the ledger | **kept** (stricter) |
| Row counts: a fixed list, compared for **equality** | the app's list, a **drop** fails | **kept** (sign-ups during a release are not a failure); the list from `deploy.json` is DF-5 |
| `konta-wyslij` dry run, crontab of the app, blog sync | none | **app** |

## 5. `verify` vs `verify-production.sh`

Already covered by DP-4: status, markers present and absent, redirects with their target, header checks (a
`content-type` entry is FIRE's "code **and** type" rule, L-135), TLS expiry (DF-6).

| FIRE | Package | Decision |
| --- | --- | --- |
| `POST` with a body and request headers (`/api/mcp` → 401, `/api/wypisz` → 200, `/kalkulator/licznik` → 204) | `GET` only | **port**: `method`, `body`, `requestHeaders` per route |
| Request headers per route: `User-Agent` of AI bots (200 and content, not a Cloudflare challenge), `Accept: text/markdown` | fixed request headers | **port** (same `requestHeaders`) |
| Two hosts (apex and app subdomain) | one base URL per run | **kept** (run verify once per host, each with its config) |
| Direct HTTPS to the server IP must fail (the firewall lets only Cloudflare in) | none | **gap** (needs the IP as an input; a warning in FIRE) |
| A 404 is a warning for a route waiting on an owner secret | pass or fail | **app** |
| sha256 of every skill equals the index digest; markers inside `<head>`; IndexNow key read from source | none | **app** |
| `<<<` instead of a pipe (SIGPIPE under `pipefail` on bodies over 64 KB) | bodies read whole in Node | **kept** (the class of bug cannot happen) |

## 6. Where each difference goes

- Ported here: optional names and the header line in `env render`; `--body` sections and the roadmap table in
  `release-notes`; `--exclude-table-data`, `--max-age-days` and the header check in `backup`; `method`, `body` and
  `requestHeaders` in `verify`.
- New gaps (after DF-7, which changes the same two files; next free numbers after DF-8, which DF-5 reserves):
  - **DF-9** `deploy-server-safety`: the server script's `status` command, file and `.env.prod` restore, `.env.prod.prev`,
    Traefik recreate, the tag in `.env.prod`, a daily cron for backup age and image prune, machine-readable lines.
  - **DF-10** `deploy-release-report`: a report job writes pipeline status and deployment history into the release
    body (uses `release-notes --body`), from the machine lines of DF-9.
  - **DF-11** `deploy-workflow-release-guards`: tag on the default branch, build args with the origin comparison,
    non-secret values for optional names, a per-deploy registry token in the stdin archive.
  - **DF-12** `deploy-cut-release`: a reusable workflow that cuts a date tag and release and dispatches the deploy.
  - **DF-13** `deploy-verify-origin-firewall`: verify checks that the server IP refuses direct HTTPS.
- FIRE-specific: listed in the README section "Parity with FIRE_TRACKER".
