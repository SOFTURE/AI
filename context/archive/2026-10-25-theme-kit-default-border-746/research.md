# Research

- Cause: Tailwind v4's preflight resets `border: 0 solid` on `*`, which leaves `border-color` at `currentColor`.
  stock shadcn/ui new-york v4 adds `@layer base { * { @apply border-border outline-ring/50; } }` in `globals.css`.
  Neither `themes/theme-notion` (`theme.css` is generated by `buildThemeCss`, tokens and `@theme inline` only;
  `sft-bridge.css`) nor `themes/theme-kit/src/base.css` (only `body`) carries it.
- The kit's scoped `preflight.css` already sets `border: 0 solid var(--border)` and the 50 % `ring` outline inside
  `[data-slot]` elements, so the bug shows only in the full-preflight wiring (README's first block), and for app markup
  without `data-slot` in both.
- `border` and `ring` are contract colour roles (`SHADCN_COLOR_ROLES` in `theme-kit/src/theme-definition.ts`), so a
  rule reading them is theme-agnostic and belongs in the kit, where every future theme gets it.
- `theme-kit/src/base.css` is imported by both README wirings of theme-notion, after `tailwindcss` (or the scoped
  preflight) and after `theme.css`, in `@layer base`. A `*` rule there comes after Tailwind's preflight in the same
  layer with the same specificity, so it wins; every `border-*` / `outline-*` utility sits in `utilities` and still
  wins over it.
- Pages of the SOFTURE packages in the scoped wiring: `@softure-ai/ui` puts its utilities in `@layer softure`, above
  `base`, and theme-notion's `sft-bridge.css` maps `--sft-color-border` to `var(--border)`, so a default border on
  those pages taking `--border` matches what the bridge already shows.
- Tests: `theme-kit/tests/stylesheets.test.ts` pins `base.css` to "only body, only `--background`/`--foreground`";
  `theme-notion/tests/theme-css.test.ts` compiles `theme.css` plus the kit's stylesheets with the real Tailwind CLI,
  so the compiled output can be asserted (the issue's acceptance).
