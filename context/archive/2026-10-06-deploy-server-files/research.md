# Research: deploy-server-files

Date: 2026-10-06 · Sources: `.github/workflows/deploy-app.yml` (DP-2, DF-2), `tools/deploy/templates/` and
`src/init/` (DP-5), `tools/deploy/README.md`, DF-5's open PR #122 (gap DF-8), GNU tar 1.35 and bash 5 tried in the
container.

## What exists

- **The deploy job** checks out only the compose file at the tag (sparse, anchored, no credentials), renders
  `.env.prod` with `softure-deploy env render`, and runs one `ssh … "<remote-command> <tag>" < .env.prod`. The key is
  bound to `/srv/<name>/deploy.sh` by `command="…",restrict` in `authorized_keys`, so stdin and
  `SSH_ORIGINAL_COMMAND` are all the script gets.
- **`deploy.sh`** (generated by `init`, owned by the app afterwards) expects `deploy <tag>`, writes stdin to
  `.env.prod` (0600) and runs `docker compose --env-file .env.prod --file docker-compose.yml` in its own folder.
  Next to it live `docker/prod/*` (`docker-compose.yml`, `traefik.yml`, `initdb/`), copied by hand, plus
  `.deployed-tag` and, with a database, `backups/`.
- **The compose file** sets `name: <name>` (a fixed project), uses named volumes for data and bind-mounts
  `./traefik.yml` (Traefik's file provider, `watch=true`) and `./initdb` (read on Postgres' first start only).
- **`deploy.json`** sits at the app's root (`init` writes it); DF-2 reads it in the `verify` job. DF-8 (from DF-5,
  not on `master` yet) wants the server's `deploy.sh` to read the row-count tables from a shipped copy.
- **Callers:** none known. `@softure-ai/deploy` 0.1.0 went to npm in DP-8, 0.1.1 with release 0.1.5 and 0.1.2 with DF-6 (all while
  this ran); no app deploys through the workflow yet, so changing the protocol breaks nobody running. An app that ran
  `init` with those versions copies the new `deploy.sh` once.

## Facts the design relies on

- **Self-update.** bash reads a script from an open file as it runs. Overwriting `deploy.sh` in place (same inode)
  would change the lines the running copy reads next; replacing it by `mv` of a new file gives the path a new inode
  and the running copy finishes from the old one (tried: `cp new tmp && mv tmp s.sh` mid-run, the old copy kept
  printing its own lines). So `deploy.sh` is installed by rename and runs from the next release.
- **Bind-mounted single files.** Docker binds the inode a file path had when the container started. `cp` onto an
  existing file keeps the inode, so a running Traefik sees the new rules; `mv` would leave it on the old file.
  Whether Traefik's watcher fires for a write made through the host path is not something to rely on, so the script
  restarts Traefik when its rules changed and the switch did not recreate it.
- **Compose recreates** a service when its configuration changes (image, command, mounts as written), not when a
  bind-mounted file's content does. Keeping the files at the same paths in `/srv/<name>/` keeps Postgres from being
  recreated on every release, which a per-release folder used as the compose project directory would do (its mount
  sources change each time).
- **tar.** GNU tar refuses members with `..` (exit 2) and strips a leading `/`, but extracts symlinks and hard links
  as they are; a member list checked before extraction (regular files and folders only, names in a narrow pattern)
  closes that. `--no-same-owner` keeps files owned by the deploy user. With `umask 077` extracted files are 0600,
  which a container's non-root user (Postgres reading `initdb/`) cannot read, so installed files get 0644 and
  folders 0755 explicitly.
- **Sparse checkout** with non-cone, anchored patterns (`/docker/prod/`, `/docker/server/deploy.sh`, `/deploy.json`)
  fetches only those paths, so the deploy job still has no `.npmrc` or `package.json` of the app when `npx` runs.

## Unknowns

- **Does FIRE's gateway ship files?** Not answerable here: DF-1 has not landed and no session can read FIRE_TRACKER.
  Recorded for DF-1, which compares the deploy workflow with FIRE's anyway.
- **Which folder is "docker/prod/"?** The folder of the `compose-file` input (default `docker/prod/`), so an app that
  moved its compose file ships the folder it lives in; no second input to keep in step.
