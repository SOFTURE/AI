# Plan: packages-first-release

Input: change.md, research.md. Complexity: small (one phase, metadata only).

## Goal

- core, db and ui lose `"private": true`.
- The 16 releasable packages are at 0.1.0 in `package.json`, `module.json` and the inline manifests.
- Every `@softure-ai/*` range (deps, peers, devDeps) and every `dependsOn` range is `^0.1.0` (blog keeps
  its optional `?`).
- Both lockfiles match, regenerated by npm.
- `scripts/release/README.md` has a "First batch release" section: the exact tag commands in dependency
  order, three per push, then approval and trusted publisher per package.
- The README status lines that say "not published yet" say 0.1.0 is prepared and waits for the tag.
- LT-2 in the queued roadmap `later` records the `release:version` gap (inline manifests).

**Out of scope:** tagging or publishing; the finish reviews and status closing of BL-8, MK-8, EN-9 and
MO-6 (they close after the tags are live); fixing `release:version` (LT-2); LT-1.

## Approach

**Chosen:** set 0.1.0 directly in one commit instead of running `release:version` 16 times. The owner
then creates the tags on the merged `master` (`git tag -a core@0.1.0 -m core@0.1.0`), which is exactly
what the release workflow checks (tag version = `package.json` = `module.json`).
Rejected: the owner runs `release:version` per package - 16 commits at the keyboard, each needing a range
commit first, and it breaks the module tests (LT-2 gap).

**Key decisions:**
| Decision | Choice | Why | Source |
| --- | --- | --- | --- |
| Version | 0.1.0 for all 16 | the roadmap items name 0.1.0 | roadmap-later |
| Ranges | `^0.1.0` | accepts 0.1.x patches, the npm default for a 0.x minor | release-rules |
| devDependency ranges | `^0.1.0` too | keeps one range per package; `npm ci` links them | research |
| Tag order | layers by dependency, three per push | GitHub ignores pushes of more than three tags; approval order makes each package installable | research |
| Template | stays private, 0.0.0 | copied, never released | change.md |

`package-lock.json`, `examples/next-app/package-lock.json`, `foundation/core/README.md`, `foundation/db/README.md`,

1. A one-off node script (not committed) sets `version` to 0.1.0, drops `private` from core/db/ui and
   rewrites every `@softure-ai/*` range `^0.0.0` to `^0.1.0` in the 16 `package.json` files.
2. `module.json` and `src/index.ts`: `"0.0.0"` → `"0.1.0"` for `version`, `^0.0.0` → `^0.1.0` in `dependsOn`.
3. The six module tests quoting `(^0.0.0)` and the privacy test fixture `notes` use `^0.1.0`.
4. `npm install --package-lock-only` at the root and in `examples/next-app`.
5. README status lines (core, db, ops, seo) and the runbook section with the tag batches:
   `core db ui` · `seo security ops` · `mailing auth analytics` · `blog privacy mcp-access` ·
   `feature-switches billing waitlist` · `marketing-kit`.
6. LT-2 row, item block and backlog entry in `later`.

**Done when:** `grep -rn '"0\.0\.0"\|\^0\.0\.0' --include=package.json --include=module.json foundation modules tools`
finds nothing; `grep -n '"private"' foundation/*/package.json` finds nothing; the gates and build pass;
`npm run release:pack -- --all --dry-run --out <tmp>` packs 16 public packages without problems.

## Risks and rollback

- A range missed in a file the grep does not cover: `tests/repo/packages.test.ts` fails on deps and
  peers. Rollback: revert the commit; nothing is published before the owner tags.
- The owner tags a commit before this merges: the workflow refuses (`private` or version mismatch), no
  publish happens.

## Decisions (auto)

- One commit with 0.1.0 instead of 16 `release:version` runs → fewer owner steps, avoids the LT-2 gap.
- auth, ops, security, feature-switches, core, db, ui released in the same batch although no item names
  them → the named packages are not installable without them.
